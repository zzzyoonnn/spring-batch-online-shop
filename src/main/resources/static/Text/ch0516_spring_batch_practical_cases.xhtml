16장. 성능 확장: 멀티스레드·파티셔닝

이 장에서 배우는 것

  • 확장 전에 단일 스레드로 먼저 측정해야 하는 이유
  • 멀티스레드 Step과 파티셔닝의 차이와 선택 기준
  • 병렬 처리에서 깨지기 쉬운 것들(순서·상태·Reader 동시성)

16.1 먼저 측정하라

공식 문서가 일관되게 권하는 순서가 있습니다. 먼저 단순한 단일 스레드로 성능을 측정한 뒤, 그것으로 부족할 때만 확장을 고려하라는 것입니다.

1. 단일 스레드로 만들어 동작시킨다
2. 실제 데이터로 처리 시간을 측정한다
3. 목표 시간 안에 끝나면 → 끝. 더 복잡하게 만들지 않는다
4. 부족하면 → 병목을 찾고, 그다음에 확장한다

병목이 Reader인지(DB 조회가 느림), Processor인지(무거운 계산), Writer인지(외부 전송)에 따라 처방이 다릅니다. 측정 없이 멀티스레드부터 도입하면, 엉뚱한 곳을 병렬화해 복잡성만 늘고 빨라지지 않습니다.

📌 핵심: 병렬화는 공짜가 아닙니다. 코드가 복잡해지고 버그가 숨기 쉬워집니다. "측정 → 병목 확인 → 그다음 확장"의 순서를 지키세요.

16.2 청크 크기 조정부터

확장 전에 가장 싸게 시도할 수 있는 것은 청크 크기 튜닝입니다. 너무 작으면 커밋이 잦아 느리고, 너무 크면 메모리와 롤백 비용이 큽니다. 100·500·1,000을 실측해 가장 빠른 값을 찾는 것만으로도 충분히 빨라지는 경우가 많습니다.

chunkSize=100   → 커밋 잦음, 안전하지만 느릴 수 있음
chunkSize=1000  → 처리량 ↑, 실패 시 롤백 범위 ↑

💡 Reader가 페이징으로 읽는다면 pageSize와 chunkSize를 맞추는 것이 보통 효율적입니다. 한 번 읽은 페이지가 한 번의 커밋과 정렬되기 때문입니다.

16.3 멀티스레드 Step

가장 간단한 병렬화는 하나의 Step을 여러 스레드로 처리하는 것입니다. TaskExecutor를 지정하면 청크들이 여러 스레드에 나뉘어 동시에 처리됩니다.

@Bean
public Step parallelStep(TaskExecutor taskExecutor) {
    return new StepBuilder("parallelStep", jobRepository)
            .<In, Out>chunk(500, transactionManager)
            .reader(threadSafeReader()) // 동시 접근에 안전해야 함!
            .processor(processor())
            .writer(writer())
            .taskExecutor(taskExecutor)
            .build();
}

여기엔 큰 함정이 있습니다. 여러 스레드가 같은 Reader를 동시에 호출하므로 Reader가 스레드 안전(thread-safe)해야 합니다. 또 처리 순서가 보장되지 않습니다. 순서에 의존하는 로직이 있으면 깨집니다.

⚠️ 멀티스레드 Step에서는 "내가 방금 읽은 다음 건"을 가정하지 마세요. 스레드마다 다른 청크를 잡아갑니다. 순서가 중요하거나 상태를 공유하는 처리에는 적합하지 않습니다.

16.4 파티셔닝

더 견고한 확장 방식은 파티셔닝(partitioning)입니다. 데이터를 겹치지 않는 구간으로 나누고, 각 구간을 독립된 Step 인스턴스가 처리합니다.

회원 ID 1 ~ 100000        → 파티션 1 (스레드/프로세스 A)
회원 ID 100001 ~ 200000   → 파티션 2 (스레드/프로세스 B)
회원 ID 200001 ~ 300000   → 파티션 3 (스레드/프로세스 C)

각 파티션은 자기 구간만 읽으므로 Reader 동시성 문제가 없고, 구간이 겹치지 않으니 데이터 경합도 없습니다. 6장에서 ID 구간을 나눠 마이그레이션한 것을, 프레임워크가 자동으로 병렬 실행해 주는 형태라고 보면 됩니다.

멀티스레드 Step:  하나의 Reader를 여러 스레드가 공유 (간단하지만 동시성 주의)
파티셔닝:        구간별로 Reader가 분리 (견고하고, 분산까지 확장 가능)

💡 파티셔닝은 한 장비 안 여러 스레드뿐 아니라, 여러 장비로 작업을 나누는 분산 처리(remote partitioning)로도 확장됩니다. 다만 그만큼 인프라가 복잡해지므로, 정말 필요할 때만 갑니다.

16.5 확장의 비용을 기억하라

병렬화하면 빨라지지만, 동시에 잃는 것이 있습니다. 처리 순서, 디버깅의 용이함, 단순함입니다. 그리고 DB·외부 API가 병목이라면, 스레드를 늘려도 그 자원의 한계 때문에 빨라지지 않거나 오히려 경합으로 느려집니다.

⚠️ 외부 API 수집(13장)을 병렬화하면 호출량이 배로 늘어 rate limit에 걸리기 쉽습니다. 자원에 제한이 있는 작업은 병렬도를 올리는 것이 역효과일 수 있습니다.

🧪 실습 — 측정하고 결정하기

  1. 6장 마이그레이션 배치를 충분히 큰 데이터(수십만 건)로 단일 스레드 실행해 시간을 잽니다.
  2. 청크 크기를 100/500/1000으로 바꿔 가장 빠른 값을 찾습니다.
  3. 그래도 부족하면 ID 구간 파티셔닝을 적용하고, 단일 스레드 대비 얼마나 빨라지는지 측정합니다.
  4. "빨라진 만큼 복잡해졌는가?"를 기록해, 확장이 값어치를 했는지 판단합니다.

이 장의 요점

  • 확장 전에 단일 스레드로 측정하고 병목을 찾습니다. 청크 크기 튜닝이 가장 싼 1차 개선입니다.
  • 멀티스레드 Step은 간단하지만 Reader 스레드 안전성과 순서 보장 문제가 있고, 파티셔닝은 구간을 나눠 더 견고하게 병렬화합니다.
  • 병렬화는 순서·단순함을 대가로 치르며, DB·외부 API가 병목이면 효과가 제한적이거나 역효과일 수 있습니다.
