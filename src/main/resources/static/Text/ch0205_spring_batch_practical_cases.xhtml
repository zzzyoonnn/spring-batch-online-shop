5장. 상품 CSV 대량 업로드

이 장에서 배우는 것

  • FlatFileItemReader로 CSV를 한 줄씩 읽어 객체로 매핑하기
  • Validation으로 상품 데이터를 검증하고, 잘못된 행을 Skip 처리하기
  • JdbcBatchItemWriter로 대량 저장하고, 실패 행을 별도 리포트로 남기기

5.1 사례 이해: 가장 흔한 배치

관리자가 상품 10만 건이 든 CSV를 업로드하면, 마켓온은 파일을 한 줄씩 읽고 검증한 뒤 상품 테이블에 저장합니다. 이건 모든 쇼핑몰에서 가장 자주 쓰는 배치입니다.

CSV 파일
 → ItemReader          (한 줄씩 읽기)
 → ItemProcessor        (상품명/가격/카테고리 검증·변환)
 → ItemWriter           (상품 테이블 저장)
 + 실패 행 리포트         (어떤 행이 왜 틀렸는지 기록)

같은 패턴으로 회원 대량 등록, 쿠폰 대량 발급, 거래처 목록 업로드, 재고 일괄 반영을 모두 처리할 수 있습니다.

📌 핵심: 파일이 크면 일반 API 요청에서 바로 처리하기 어렵습니다. 요청이 길어지고, 실패하면 어디까지 처리됐는지 알 수 없습니다. 배치는 진행 상태를 메타테이블에 남기고 실패 지점부터 재시작할 수 있습니다.

5.2 입력 모델과 도메인

CSV 한 줄을 담을 DTO와, 저장할 엔티티를 나눕니다. 검증은 입력 DTO에 Validation 애너테이션으로 붙입니다.

@Getter @Setter
public class ProductCsvRow {
    @NotBlank(message = "상품명은 필수입니다")
    private String name;

    @NotNull @Min(value = 0, message = "가격은 0 이상이어야 합니다")
    private Integer price;

    @NotBlank(message = "카테고리는 필수입니다")
    private String categoryCode;
}

CSV 예시:

name,price,categoryCode
무선 마우스,12900,ELEC
기계식 키보드,89000,ELEC
,15000,ELEC        ← 상품명 누락 (검증 실패)
USB 허브,-100,ELEC ← 가격 음수 (검증 실패)

5.3 Reader: FlatFileItemReader

FlatFileItemReader는 텍스트 파일을 한 줄씩 읽어 객체로 매핑합니다. 구분자·컬럼명·매핑 대상만 지정하면 됩니다.

@Bean
@StepScope // 잡 파라미터로 파일 경로를 주입받기 위해
public FlatFileItemReader<ProductCsvRow> productReader(
        @Value("#{jobParameters['filePath']}") String filePath) {
    return new FlatFileItemReaderBuilder<ProductCsvRow>()
            .name("productReader")
            .resource(new FileSystemResource(filePath))
            .linesToSkip(1) // 헤더 한 줄 건너뜀
            .delimited().delimiter(",")
            .names("name", "price", "categoryCode")
            .targetType(ProductCsvRow.class)
            .build();
}

💡 @StepScope는 "Step이 실행될 때" 빈을 생성하게 해, jobParameters에서 값(여기서는 업로드된 파일 경로)을 주입받을 수 있게 합니다. 파일·기준일처럼 실행마다 달라지는 입력을 다룰 때 거의 항상 함께 등장합니다.

5.4 Processor: 검증과 변환

Processor에서 Validation으로 검증하고, 통과한 행만 엔티티로 변환합니다. 검증 실패는 예외를 던져 Skip 흐름으로 보냅니다.

@Component
@RequiredArgsConstructor
public class ProductProcessor implements ItemProcessor<ProductCsvRow, Product> {

    private final Validator validator;
    private final CategoryRepository categoryRepository;

    @Override
    public Product process(ProductCsvRow row) {
        Set<ConstraintViolation<ProductCsvRow>> violations = validator.validate(row);
        if (!violations.isEmpty()) {
            String msg = violations.iterator().next().getMessage();
            throw new InvalidProductRowException(row, msg); // → Skip 대상
        }
        Long categoryId = categoryRepository.findIdByCode(row.getCategoryCode());
        if (categoryId == null) {
            throw new InvalidProductRowException(row, "존재하지 않는 카테고리");
        }
        return Product.of(row.getName(), row.getPrice(), categoryId);
    }
}

💡 카테고리 코드를 ID로 바꾸는 것도 Processor의 일입니다. 이런 "코드 → 내부 식별자" 매핑은 CSV 업로드에서 단골로 등장합니다.

5.5 Writer와 Step 조립: 실패 행을 남기는 Skip

JdbcBatchItemWriter는 Chunk를 모아 한 번에 INSERT합니다. 핵심은 잘못된 행 하나 때문에 전체를 실패시키지 않는 것입니다. Step에 Skip 정책을 걸고, Skip된 행은 리스너로 잡아 product_import_error 테이블에 기록합니다.

@Bean
public Step productImportStep() {
    return new StepBuilder("productImportStep", jobRepository)
            .<ProductCsvRow, Product>chunk(500, transactionManager)
            .reader(productReader(null))
            .processor(productProcessor)
            .writer(productWriter)
            .faultTolerant()
            .skip(InvalidProductRowException.class)
            .skipLimit(1000) // 최대 1,000행까지 건너뜀
            .listener(productSkipListener) // 스킵된 행을 error 테이블에 기록
            .build();
}

실패 행을 담는 테이블은 다음과 같습니다.

CREATE TABLE product_import_error (
    id           BIGINT AUTO_INCREMENT PRIMARY KEY,
    row_number   INT,
    product_name VARCHAR(255),
    error_message VARCHAR(500),
    raw_data     TEXT,
    created_at   DATETIME
);

이렇게 하면 업로드가 끝난 뒤 관리자가 "10만 건 중 37건 실패, 사유는 이러이러함"을 화면에서 확인하고 그 행만 고쳐 다시 올릴 수 있습니다.

⚠️ Skip이 항상 옳은 건 아닙니다. 거래처 목록처럼 일부 누락이 허용되는 데이터는 Skip이 적절하지만, 금융·정산처럼 정확성이 생명인 데이터는 한 건만 틀려도 전체를 멈추는 편이 안전할 수 있습니다. 업무 성격에 따라 결정하세요(15장에서 정책을 깊이 다룹니다).

5.6 화면에 붙이기

4장의 운영 콘솔에 업로드 폼을 추가합니다. 파일을 받아 서버 임시 경로에 저장하고, 그 경로를 JobParameter로 넘깁니다.

@PostMapping("/jobs/product-import")
public String runProductImport(@RequestParam MultipartFile file) throws Exception {
    Path saved = saveToTemp(file); // 임시 디렉터리에 저장
    JobParameters params = new JobParametersBuilder()
            .addString("filePath", saved.toString())
            .addLong("runAt", System.currentTimeMillis())
            .toJobParameters();
    jobLauncher.run(productImportJob, params);
    return "redirect:/admin";
}

🧪 실습 — CSV 업로드 배치 만들기

  1. 위 모델·Reader·Processor·Writer·Step을 com.marketon.batch.product에 구현합니다.
  2. 5.2의 예시처럼 정상 행과 오류 행(상품명 누락, 음수 가격)을 섞은 CSV를 만듭니다.
  3. 콘솔에서 업로드한 뒤, product 테이블에 정상 행만 들어갔는지, product_import_error에 오류 행 2건이 사유와 함께 남았는지 확인합니다.
  4. Chunk 크기를 500 → 50으로 바꿔 다시 실행하고, 동작은 같지만 커밋 횟수가 늘어남을 관찰합니다.

이 장의 요점

  • FlatFileItemReader로 CSV를 객체로 매핑하고, @StepScope로 업로드 파일 경로를 JobParameter로 주입받습니다.
  • Processor에서 Validation으로 검증·변환하고, 검증 실패는 예외로 Skip 흐름에 태웁니다.
  • faultTolerant().skip()과 리스너로 잘못된 행만 건너뛰고 product_import_error에 사유를 남겨, 관리자가 실패 행만 고쳐 재업로드할 수 있게 합니다.

다음 장에서는 파일이 아니라 DB에서 DB로 흐르는 사례를 다룹니다. 회원 ID 구간을 나눠 레거시 데이터를 새 구조로 옮기고, 운영 데이터를 안전하게 보정하는 마이그레이션 배치를 만듭니다.
