3장. Spring Batch 핵심 구조

3.1 Job, Step, Chunk

Spring Batch의 구조는 러시아 인형처럼 포개져 있습니다.

Job  (하나의 배치 작업 전체, 예: 정산 배치)
 └─ Step  (작업의 한 단계, 예: 정산 대상 조회 / 수수료 계산 / 저장)
     └─ Chunk  (Step 안에서 한 번에 커밋하는 묶음, 예: 1,000건)
         └─ Item  (낱개 데이터 한 건, 예: 주문 한 건)

Job은 "정산 배치"처럼 의미 있는 작업 한 덩어리입니다. Step은 그 작업의 한 단계이고, 하나의 Job은 여러 Step을 순서대로 실행할 수 있습니다. 그리고 각 Step 안에서 데이터를 Chunk(청크) 단위로 끊어 처리합니다.

Chunk가 이 책의 관통 원칙 "작게 나눠 처리하기"의 실체입니다. Chunk 크기를 1,000으로 정하면, Reader가 1,000건을 읽어 Processor로 가공하고 Writer로 저장한 뒤 한 번 커밋합니다. 그다음 1,000건을 또 묶어 처리합니다. 이렇게 하면 10만 건을 한 트랜잭션에 욱여넣지 않고, 1,000건씩 100번에 나눠 안전하게 처리할 수 있습니다.

📌 핵심: Chunk는 "읽기·가공·쓰기를 묶어 한 번에 커밋하는 단위"입니다. Chunk 하나가 실패하면 그 Chunk만 롤백되고, 이미 커밋된 앞쪽 Chunk는 살아남습니다.

3.2 Reader → Processor → Writer

Step 안에서 데이터는 세 손을 거칩니다.

  • ItemReader — 데이터를 한 건씩 읽어 옵니다. CSV 파일, DB, 외부 API 등 출처는 다양합니다.
  • ItemProcessor — 읽은 한 건을 가공·검증·변환합니다. null을 반환하면 그 건은 Writer로 넘어가지 않고 걸러집니다(필터링).
  • ItemWriter — 가공된 묶음(Chunk)을 한꺼번에 저장하거나 전달합니다.
CSV 한 줄  →  Reader  →  Processor(검증·변환)  →  Writer(DB 저장)

Processor는 선택입니다. 단순히 읽어서 그대로 저장만 한다면 생략할 수 있습니다. 이 세 인터페이스의 구현을 갈아 끼우는 것만으로 "파일→DB", "DB→DB", "DB→API", "API→DB" 같은 모든 조합을 만들 수 있습니다(부록 B 참조).

3.3 Spring Batch 5 방식으로 Job 정의하기

Spring Boot 3 / Spring Batch 5부터는 설정 방식이 단순해졌습니다. 과거에 쓰던 @EnableBatchProcessing이나 JobBuilderFactory·StepBuilderFactory는 더 이상 필요하지 않습니다. 대신 스프링이 자동 구성해 주는 JobRepository와 PlatformTransactionManager를 주입받아, JobBuilder·StepBuilder로 직접 조립합니다.

💡 이 JobBuilder·StepBuilder 패턴은 최신 안정 버전인 Spring Batch 6에서도 그대로 유효합니다. Spring Boot 자동 구성을 쓰면 6에서도 별도 애너테이션이 필요 없습니다(직접 구성할 때만 6에서 새로 생긴 @EnableJdbcJobRepository 등을 씁니다). 이 책의 예제 코드는 Spring Batch 5.2 이상과 6.0에서 동일하게 동작합니다. 사용하는 버전은 [start.spring.io](https://start.spring.io)에서 생성하면 호환 버전이 자동으로 맞춰집니다.

가장 단순한 "Hello Batch"를 보겠습니다. 데이터를 읽지 않고 한 번만 실행되는 Tasklet Step입니다.

@Configuration
@RequiredArgsConstructor
public class HelloJobConfig {

    private final JobRepository jobRepository;
    private final PlatformTransactionManager transactionManager;

    @Bean
    public Job helloJob() {
        return new JobBuilder("helloJob", jobRepository)
                .start(helloStep())
                .build();
    }

    @Bean
    public Step helloStep() {
        return new StepBuilder("helloStep", jobRepository)
                .tasklet((contribution, chunkContext) -> {
                    System.out.println("Hello, Spring Batch!");
                    return RepeatStatus.FINISHED;
                }, transactionManager)
                .build();
    }
}

여기서 두 가지를 기억하세요. 첫째, JobBuilder와 StepBuilder의 생성자에 이름과 jobRepository를 넘깁니다. 이름은 메타테이블에 그대로 기록됩니다. 둘째, tasklet과 청크 기반 Step 모두 transactionManager를 요구합니다. 트랜잭션 경계를 스프링이 관리하기 때문입니다.

💡 Tasklet vs Chunk — Step에는 두 가지 방식이 있습니다. Tasklet은 "한 번 실행하고 끝나는 단순 작업"(예: 테이블 초기화, 파일 정리)에, Chunk 기반은 "대량 데이터를 묶어 반복 처리"에 씁니다. 사례 대부분은 Chunk 기반을 씁니다.

3.4 청크 기반 Step의 모양

5장부터 본격적으로 쓸 Chunk 기반 Step의 뼈대는 다음과 같습니다. <I, O>는 Reader가 읽는 타입(I)과 Writer가 받는 타입(O)입니다.

@Bean
public Step sampleStep() {
    return new StepBuilder("sampleStep", jobRepository)
            .<InputType, OutputType>chunk(1000, transactionManager) // 청크 크기 1,000
            .reader(reader())
            .processor(processor())
            .writer(writer())
            .build();
}

chunk(1000, transactionManager) 한 줄에 관통 원칙이 담겨 있습니다. 1,000건마다 커밋하므로, 5만 번째 건에서 실패해도 앞의 4만 9천 건은 안전하게 저장되어 있고, 재시작하면 5만 번째부터 이어 갑니다.

⚠️ 청크 크기는 정답이 없습니다. 너무 작으면 커밋이 잦아 느리고, 너무 크면 실패 시 롤백 범위가 커지고 메모리를 많이 씁니다. 보통 100~1,000 사이에서 시작해 측정으로 조정합니다(15·16장).

3.5 메타테이블로 결과 확인하기

Job을 실행하면 Spring Batch는 결과를 메타테이블에 남깁니다. 정상 종료한 실행은 BATCH_JOB_EXECUTION.STATUS가 COMPLETED로 기록되고, Step별 읽기/쓰기 건수는 BATCH_STEP_EXECUTION의 READ_COUNT·WRITE_COUNT에 남습니다.

SELECT job_instance_id, status, start_time, end_time
FROM BATCH_JOB_EXECUTION
ORDER BY job_execution_id DESC;

이 한 줄이 운영에서 "어제 새벽 정산이 잘 돌았나?"를 확인하는 출발점입니다.

이 장의 요점

  • Job은 작업 전체, Step은 한 단계, Chunk는 한 번에 커밋하는 묶음입니다. Chunk가 "작게 나눠 처리하기"의 실체입니다.
  • 데이터는 Reader(읽기) → Processor(가공·검증) → Writer(쓰기)를 거치며, Processor가 null을 반환하면 그 건은 걸러집니다.
  • Spring Batch 5에서는 JobRepository·PlatformTransactionManager를 주입받아 JobBuilder·StepBuilder로 Job/Step을 조립하고, 결과는 메타테이블로 확인합니다.
