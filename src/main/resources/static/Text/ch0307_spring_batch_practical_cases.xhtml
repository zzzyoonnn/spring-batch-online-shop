7장. 매일 새벽 정산 배치

이 장에서 배우는 것

  • 정산 배치의 흐름과 멱등성(idempotency)이 왜 절대적인지
  • 기준일 JobParameter와 UNIQUE 제약으로 중복 정산을 막는 법
  • 정산 상태값(READY→CONFIRMED→PAID)으로 안전하게 재실행하기

7.1 사례 이해: 정확성이 생명인 배치

마켓온은 하루 동안 발생한 주문을 기준으로 판매자별 정산 금액을 매일 새벽 계산합니다.

전날 주문 데이터 조회
 → 결제 완료 주문 필터링
 → 환불/취소 제외
 → 판매자 수수료 계산
 → 판매자별 정산 테이블 저장

정산·PG 결제 정산·포인트 정산·쿠폰 정산·배송비 정산이 모두 이 패턴입니다. 그리고 이들의 공통점은 다음과 같습니다.

대상 데이터가 많다
정확성이 매우 중요하다
실패하면 재처리해야 한다
작업 이력이 남아야 한다
중복 정산을 절대 막아야 한다

Spring Batch는 Job·Step 실행 이력과 성공/실패 상태를 관리하므로 이런 업무에 잘 맞습니다.

📌 핵심: 정산 배치의 1번 요구사항은 "빠르게"가 아니라 "같은 날짜를 두 번 돌려도 정산금이 두 배가 되지 않게"입니다. 이것이 멱등성입니다.

7.2 멱등성이란

멱등성(idempotency)은 "같은 작업을 여러 번 해도 결과가 한 번 한 것과 같다"는 성질입니다. 새벽 정산이 네트워크 문제로 두 번 실행되거나, 운영자가 실수로 다시 눌러도 정산금이 두 번 쌓이면 안 됩니다.

나쁜 방식:
  INSERT INTO settlement ...        ← 돌릴 때마다 한 줄씩 추가됨 (중복!)

좋은 방식:
  (정산 기준일 + 판매자 ID)로 기존 정산을 먼저 확인
  있으면 → 업데이트 또는 삭제 후 재생성
  없으면 → 신규 생성

멱등성을 만드는 방법은 크게 세 가지이고, 보통 함께 씁니다.

  1. JobParameter로 기준일 고정 — 같은 날짜로는 두 번 성공 실행되지 않게(4장에서 본 동작).
  2. UNIQUE 제약 — DB 차원에서 중복 데이터를 물리적으로 거부.
  3. 상태값 관리 — 정산의 생애주기를 상태로 추적.

7.3 settlement 테이블과 UNIQUE 제약

정산 결과 테이블을 다음과 같이 설계합니다. 핵심은 마지막의 UNIQUE 제약입니다.

CREATE TABLE settlement (
    id                 BIGINT AUTO_INCREMENT PRIMARY KEY,
    settlement_date    DATE        NOT NULL,
    seller_id          BIGINT      NOT NULL,
    total_order_amount BIGINT      NOT NULL,
    commission_amount  BIGINT      NOT NULL,
    settlement_amount  BIGINT      NOT NULL,
    status             VARCHAR(20) NOT NULL,  -- READY/CONFIRMED/PAID
    created_at         DATETIME    NOT NULL,
    UNIQUE KEY uk_settlement (settlement_date, seller_id)
);

UNIQUE (settlement_date, seller_id) 덕분에, 같은 날짜·같은 판매자의 정산이 두 번 INSERT되려 하면 DB가 거부합니다. 코드에 버그가 있어도 데이터가 망가지지 않는 마지막 방어선입니다.

⚠️ 멱등성을 애플리케이션 코드(중복 체크)에만 의존하지 마세요. 동시 실행이나 타이밍 문제로 체크를 통과해 버리는 경우가 있습니다. DB UNIQUE 제약은 그 틈을 막는 안전장치입니다.

7.4 Job 구성: 기준일을 받아 다시 만들기

정산 Job은 기준일을 파라미터로 받고, 그 날짜의 기존 정산을 먼저 지운 뒤 다시 계산하는 방식으로 멱등성을 보장합니다(삭제 후 재생성).

@Bean
public Job dailySettlementJob() {
    return new JobBuilder("dailySettlementJob", jobRepository)
            .start(deletePreviousStep())   // 1. 해당 기준일 기존 정산 삭제
            .next(calculateSettlementStep()) // 2. 주문 조회→수수료 계산→정산 저장
            .next(settlementReportStep())   // 3. 결과 리포트
            .build();
}

수수료 계산은 Processor에서 수행합니다.

@Component
public class SettlementProcessor implements ItemProcessor<Order, SettlementLine> {
    @Override
    public SettlementLine process(Order order) {
        long commission = Math.round(order.getAmount() * order.getCommissionRate());
        long settlement = order.getAmount() - commission;
        return new SettlementLine(order.getSellerId(), order.getAmount(),
                commission, settlement);
    }
}

💡 판매자별로 합산이 필요하면, Writer에서 seller_id 기준으로 집계해 settlement에 한 줄씩 upsert하거나, 별도 집계 Step을 둡니다. 8장의 집계 패턴과 같은 원리입니다.

화면에서는 기준일을 골라 실행합니다.

JobParameters params = new JobParametersBuilder()
        .addString("date", "2026-06-29")
        .toJobParameters();
jobLauncher.run(dailySettlementJob, params);

date=2026-06-29로 한 번 성공하면, 같은 날짜로는 다시 실행되지 않습니다(JobInstanceAlreadyComplete). 6월 29일 정산을 강제로 다시 만들고 싶다면, 정산 데이터를 정리하고 새 실행으로 재처리하는 운영 절차를 둡니다.

7.5 정산 상태값으로 생애주기 관리

정산금은 계산했다고 끝이 아니라, 검토하고 실제로 지급하는 과정을 거칩니다. 상태값으로 이 흐름을 추적합니다.

READY → CALCULATED → CONFIRMED → PAID
계산됨   집계 완료     담당자 확인   지급 완료

상태를 두면 안전한 재실행이 쉬워집니다. 예를 들어 PAID 상태가 된 정산은 배치가 다시 건드리지 않도록 막아, 이미 지급된 돈을 재계산해 덮어쓰는 사고를 방지할 수 있습니다.

⚠️ "삭제 후 재생성"은 아직 지급 전(READY/CALCULATED) 정산에만 적용하세요. 이미 CONFIRMED/PAID된 정산을 함부로 지우면 회계 사고가 됩니다. 재실행 정책은 상태값을 반드시 함께 봐야 합니다.

🧪 실습 — 두 번 돌려도 같은 결과

  1. order 테이블에 특정 날짜의 주문(결제 완료·환불 섞어서)을 넣습니다.
  2. date=해당일로 정산 Job을 실행하고 settlement 결과를 기록합니다.
  3. 같은 날짜로 다시 실행을 시도해, 막히는 것을 확인합니다.
  4. "삭제 후 재생성" 운영 절차로 강제 재처리한 뒤, 정산 금액이 2번째에도 동일한지 확인합니다. 금액이 두 배가 되면 멱등성이 깨진 것입니다.

이 장의 요점

  • 정산 배치의 최우선 요구사항은 멱등성입니다. 같은 기준일을 두 번 돌려도 결과가 같아야 합니다.
  • 멱등성은 기준일 JobParameter(중복 실행 차단) + UNIQUE 제약(DB 방어선) + 상태값(생애주기 관리)을 함께 써서 보장합니다.
  • 재계산은 "삭제 후 재생성"으로 구현하되, 이미 확정·지급된 정산은 상태값으로 보호합니다.

다음 장에서는 같은 "DB→집계→DB" 패턴을 통계·리포트에 적용합니다. 매일 새벽 전날 데이터를 집계해 대시보드용 테이블을 만들고, 기준일별로 다시 생성할 수 있게 구성합니다.
