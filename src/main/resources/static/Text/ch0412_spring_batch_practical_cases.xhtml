12장. 만료·삭제·아카이빙

이 장에서 배우는 것

  • 오래된 데이터를 아카이브로 옮기고 삭제하는 흐름
  • 대량 삭제를 Chunk 단위로 나눠 DB 부하를 분산하는 법
  • 삭제 전 이관(아카이빙)으로 되돌릴 수 있게 만들기

12.1 사례 이해: 쌓이면 무거워진다

운영 데이터가 계속 쌓이면 DB가 무거워집니다. 오래된 데이터를 별도 저장소로 옮기거나 삭제하는 작업이 필요합니다.

3년 지난 로그 조회
 → 아카이브 테이블 또는 파일로 저장
 → 원본 테이블에서 삭제

오래된 접속 로그 삭제, 만료된 인증 토큰 삭제, 기간 지난 임시 파일 정리, 오래된 주문 이력 아카이빙, 만료 쿠폰 상태 변경이 모두 이 사례입니다.

📌 핵심: 삭제·아카이빙의 핵심 위험은 "한 번에 너무 많이"입니다. 100만 건을 한 DELETE로 지우면 DB가 휘청합니다. 나눠서 처리해야 합니다.

12.2 한 번에 지우지 말 것

대량 삭제를 한 문장으로 처리하면 긴 트랜잭션, 락(lock) 점유, 복제 지연, 언두 로그 폭증으로 운영 DB에 부담을 줍니다.

한 번에 100만 건 DELETE         ❌  DB가 멈출 수 있음
1,000건씩 Chunk 처리            ✅  부하를 잘게 나눔

Spring Batch의 Chunk가 정확히 이 문제를 위한 도구입니다. 1,000건 읽어 아카이브로 옮기고 원본에서 지우고 커밋, 다시 1,000건. 중간에 멈춰도 이미 처리된 묶음은 안전하고, 다시 시작하면 남은 것부터 이어 갑니다.

📌 핵심: 이 장은 관통 원칙 "한 번에 다 하지 말고 작게 나눠 처리하라"가 가장 직접적으로 드러나는 사례입니다.

12.3 흐름: 옮기고 나서 지운다

순서가 중요합니다. 먼저 아카이브에 안전하게 옮긴 뒤 원본을 지웁니다. 반대로 하면 옮기다 실패했을 때 원본이 이미 사라져 복구할 수 없습니다.

@Bean
public Job archiveOldLogJob() {
    return new JobBuilder("archiveOldLogJob", jobRepository)
            .start(archiveStep())   // 1. 오래된 로그를 archive 테이블로 복사
            .next(deleteStep())     // 2. 복사 완료된 로그를 원본에서 삭제
            .build();
}

기준일은 파라미터로 받습니다. cutoff=2023-06-30이면 그 이전 데이터가 대상입니다.

@Bean
@StepScope
public JdbcPagingItemReader<AccessLog> oldLogReader(
        @Value("#{jobParameters['cutoff']}") String cutoff) {
    // WHERE created_at < :cutoff ORDER BY id
    // ...
}

💡 아카이브 대상은 별도 DB나 저렴한 저장소(예: 콜드 스토리지, 파일)로 옮기는 경우가 많습니다. Writer를 갈아 끼우면 같은 흐름으로 파일·외부 저장소에 쓸 수 있습니다.

12.4 삭제 Step에서 주의할 점

삭제 Step은 "방금 아카이브한 것"만 정확히 지워야 합니다. 가장 안전한 방법은 아카이브 Step에서 처리한 ID 범위/플래그를 기준으로 삭제하는 것입니다.

방법 A: archived = true 플래그를 켠 뒤, 그 행만 삭제
방법 B: 아카이브한 id 목록을 기준으로 삭제

또한 삭제도 Chunk 단위로 나눕니다. Reader로 삭제 대상을 읽고 Writer에서 DELETE ... WHERE id IN (...)을 Chunk 크기만큼 실행하면, 락 점유 시간이 짧게 유지됩니다.

⚠️ 삭제 배치는 되돌릴 수 없는 작업입니다. 운영 적용 전 반드시 ① cutoff 파라미터가 맞는지, ② 아카이브가 먼저 끝났는지, ③ 삭제 건수가 예상 범위인지 확인하는 절차를 두세요. 가능하면 먼저 SELECT COUNT(*)로 대상 건수를 점검하는 단계를 둡니다.

🧪 실습 — 오래된 접속 로그 아카이빙

  1. access_log에 최근부터 3년 이전까지 분포한 로그를 넣습니다.
  2. cutoff를 지정해 archiveOldLogJob을 실행합니다.
  3. 오래된 로그가 access_log_archive로 옮겨지고 원본에서 사라졌는지, 최근 로그는 그대로인지 확인합니다.
  4. Chunk 크기를 100으로 두고, 처리가 여러 번에 나눠 커밋되는 것을 로그로 관찰합니다.

이 장의 요점

  • 오래된 데이터 삭제·아카이빙은 "한 번에 너무 많이"가 가장 큰 위험이며, Chunk 단위로 나눠 DB 부하를 분산합니다.
  • 항상 아카이브에 먼저 안전하게 옮긴 뒤 원본을 삭제해, 실패 시에도 데이터를 잃지 않게 합니다.
  • 삭제는 되돌릴 수 없으므로 기준일·대상 건수를 사전 점검하는 절차를 반드시 둡니다.

다음 장에서는 외부 세계와 연결합니다. 외부 API에서 데이터를 가져와 저장하는 사례에서, 일시적 실패를 견디는 Retry 정책과 중복 저장 방지를 다룹니다.
