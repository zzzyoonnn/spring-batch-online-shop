6장. DB 마이그레이션과 데이터 보정

이 장에서 배우는 것

  • JdbcPagingItemReader로 대량 DB 데이터를 구간 단위로 안전하게 읽기
  • 변경 전 백업 → 검증 → 반영의 보정 배치 흐름
  • 운영 DB를 직접 고치는 작업에서 사고를 줄이는 설계 원칙

6.1 사례 이해: 한 번에 안 끝나는 작업

기존 시스템의 데이터를 새 구조로 옮기거나, 잘못 저장된 데이터를 일괄 보정하는 일은 한 번에 끝나지 않습니다. 중간에 실패할 수 있고, 특정 구간만 다시 처리해야 할 수도 있습니다.

레거시 회원 테이블 조회
 → 새 회원 정책에 맞게 변환
 → 신규 테이블 저장

이런 업무가 모두 여기에 해당합니다.

레거시 DB → 신규 DB 이관
주소 데이터 정규화
전화번호 포맷 통일 (010-1234-5678)
암호화되지 않은 개인정보 암호화
잘못된 상태값 보정
기존 주문 데이터 재분류

📌 핵심: 마이그레이션·보정 배치의 본질은 "구간을 나눠, 실패하면 그 구간만 다시 돌리는 것"입니다. 전체를 한 트랜잭션에 묶는 순간 재시작이 불가능해집니다.

6.2 Reader: JdbcPagingItemReader로 구간 나누기

대량 DB를 읽을 때 SELECT * FROM member를 한 번에 메모리로 올리면 위험합니다. JdbcPagingItemReader는 정렬 키를 기준으로 페이지 단위로 끊어 읽어, 수백만 건도 일정한 메모리로 처리합니다.

@Bean
public JdbcPagingItemReader<LegacyMember> legacyMemberReader(DataSource dataSource) {
    Map<String, Order> sortKeys = new LinkedHashMap<>();
    sortKeys.put("id", Order.ASCENDING); // 반드시 유니크하고 정렬 가능한 키

    return new JdbcPagingItemReaderBuilder<LegacyMember>()
            .name("legacyMemberReader")
            .dataSource(dataSource)
            .selectClause("SELECT id, name, phone, address")
            .fromClause("FROM legacy_member")
            .whereClause("WHERE migrated = false")
            .sortKeys(sortKeys)
            .pageSize(1000)
            .rowMapper((rs, n) -> new LegacyMember(
                    rs.getLong("id"), rs.getString("name"),
                    rs.getString("phone"), rs.getString("address")))
            .build();
}

💡 정렬 키는 유니크하고 변하지 않는 값(보통 PK)이어야 합니다. 중복되거나 중간에 바뀌는 값을 키로 쓰면 페이지 경계에서 데이터가 빠지거나 중복 처리될 수 있습니다.

whereClause에 migrated = false를 둔 것도 중요합니다. 이미 옮긴 데이터는 다시 읽지 않으므로, 배치가 중간에 멈췄다 다시 시작해도 이어서 처리됩니다. 이것이 DB→DB 배치에서 멱등성을 만드는 가장 간단한 방법입니다.

6.3 Processor: 변환과 보정 규칙

전화번호 포맷 통일을 예로 들겠습니다. 01012345678, 010-1234-5678, +82 10 1234 5678처럼 제각각인 값을 한 형식으로 정규화합니다.

@Component
public class MemberMigrationProcessor
        implements ItemProcessor<LegacyMember, Member> {

    @Override
    public Member process(LegacyMember src) {
        String phone = normalizePhone(src.getPhone()); // 010-1234-5678 형태로
        String address = normalizeAddress(src.getAddress());
        return Member.migratedOf(src.getId(), src.getName(), phone, address);
    }
}

⚠️ 변환 규칙이 모든 데이터를 다 처리하지 못하는 경우를 늘 가정하세요. 정규화가 불가능한 값(예: 자릿수가 안 맞는 전화번호)은 예외로 던져 Skip하고 별도 리포트로 남기면, 사람이 수작업으로 확인할 수 있습니다(5장 패턴과 동일).

6.4 안전한 보정의 5단계

운영 DB를 직접 수정하는 보정 배치는 특히 조심해야 합니다. 권장 흐름은 다음과 같으며, 각 단계를 Step으로 나누면 장애 분석과 재실행이 쉬워집니다.

1. 대상 데이터 조회        Step 1
2. 변경 전 값 백업          Step 2  (예: member_backup 테이블에 원본 복사)
3. 변경 예정 결과 검증       Step 3  (샘플 비교·건수 확인)
4. 실제 반영               Step 4
5. 반영 결과 리포트 생성     Step 5
@Bean
public Job memberMigrationJob() {
    return new JobBuilder("memberMigrationJob", jobRepository)
            .start(backupStep())     // 2. 원본 백업
            .next(migrateStep())     // 4. 변환·반영 (Reader→Processor→Writer)
            .next(reportStep())      // 5. 결과 리포트
            .build();
}

💡 백업 Step을 앞에 두면, 보정 결과가 잘못됐을 때 백업 테이블로 되돌릴 수 있습니다. "되돌릴 수 있는가?"는 운영 배치를 만들 때 항상 던져야 할 질문입니다.

6.5 구간을 나눠 여러 번 돌리기

수백만 건이라면 한 번에 다 돌리기보다, ID 구간을 파라미터로 나눠 여러 번 실행하는 편이 운영하기 좋습니다.

memberMigrationJob fromId=1       toId=100000
memberMigrationJob fromId=100001  toId=200000
memberMigrationJob fromId=200001  toId=300000

whereClause를 WHERE id BETWEEN :fromId AND :toId로 두고 파라미터를 주입하면, 한 구간이 실패해도 그 구간만 다시 돌리면 됩니다. 새벽 시간대를 나눠 부하를 분산할 수도 있습니다.

⚠️ 구간 분할 배치는 구간이 겹치거나 빠지지 않도록 경계를 명확히 하세요. BETWEEN은 양 끝을 포함하므로, 다음 구간은 반드시 이전 toId + 1부터 시작해야 합니다.

🧪 실습 — 전화번호 정규화 보정

  1. legacy_member에 다양한 포맷의 전화번호 샘플 30건을 넣습니다(일부는 정규화 불가능한 깨진 값).
  2. 백업 → 변환 → 리포트 3-Step Job을 구성하고 콘솔에서 실행합니다.
  3. member_backup에 원본이 남았는지, member에 정규화된 값이 들어갔는지, 깨진 값은 Skip되어 리포트에 남았는지 확인합니다.
  4. migrated 플래그를 활용해, 절반쯤 처리된 상태에서 다시 실행해도 중복 처리되지 않음을 확인합니다.

이 장의 요점

  • JdbcPagingItemReader로 정렬 키 기준 페이지 단위로 읽으면, 수백만 건도 일정한 메모리로 안전하게 처리합니다.
  • migrated 플래그나 ID 구간(fromId~toId)으로 처리 범위를 제어하면, 중간에 멈춰도 이어서·다시 돌려도 안전합니다.
  • 운영 DB 보정은 "백업 → 검증 → 반영 → 리포트"로 Step을 나눠, 되돌릴 수 있고 추적 가능하게 만듭니다.

다음 장에서는 정확성이 생명인 사례, 매일 새벽 정산 배치로 들어갑니다. 같은 날짜를 두 번 돌려도 정산금이 두 배가 되지 않게 하는 멱등성 설계가 이 장의 주인공입니다.
