8장. 통계·리포트 집계

이 장에서 배우는 것

  • 실시간 집계 대신 배치로 미리 집계 테이블을 만드는 이유
  • 기준일 JobParameter로 특정 날짜만 다시 집계하는 구조
  • 집계 결과를 대시보드 화면에 빠르게 보여 주기

8.1 사례 이해: 미리 계산해 두기

마켓온 관리자 대시보드는 일별 매출, 카테고리별 매출, 판매자별 매출을 보여 줍니다. 이 숫자를 화면을 열 때마다 주문 원장 수백만 건에서 GROUP BY로 계산하면 DB가 버티지 못합니다.

실시간 계산 방식:
  화면 열 때마다 주문 테이블 수백만 건을 GROUP BY  →  느리고 무겁다

배치 집계 방식:
  새벽에 한 번 집계해 통계 테이블에 저장
  화면에서는 집계 테이블만 조회       →  즉시 응답

이 패턴으로 일별 매출 통계, 월별 가입자 통계, 상품별 판매량, 검색어 랭킹, 인기 게시글 집계를 모두 만듭니다.

📌 핵심: 통계 배치의 본질은 "무거운 계산을 트래픽 없는 시간에 미리 해 두고, 화면은 가벼운 조회만 하게" 만드는 것입니다.

8.2 집계 흐름과 테이블

전날 주문 원장을 읽어 일별·카테고리별·판매자별로 집계해 통계 테이블에 저장합니다.

주문 원장 데이터
 → 일별 매출 집계
 → 카테고리별 매출 집계
 → 판매자별 매출 집계
 → 통계 테이블 저장

집계 결과 테이블 예:

CREATE TABLE daily_sales_stat (
    stat_date     DATE        NOT NULL,
    category_code VARCHAR(40) NOT NULL,
    order_count   INT         NOT NULL,
    sales_amount  BIGINT      NOT NULL,
    PRIMARY KEY (stat_date, category_code)
);

PRIMARY KEY (stat_date, category_code)가 정산의 UNIQUE 제약과 같은 역할을 합니다. 같은 날짜·카테고리 통계가 중복으로 쌓이지 않게 막습니다.

8.3 기준일을 파라미터로 받기

통계 배치는 거의 항상 기준일을 파라미터로 받는 구조가 좋습니다. 특정 날짜 통계가 잘못됐을 때 그 날짜만 다시 생성할 수 있기 때문입니다.

@Bean
public Job dailySalesJob() {
    return new JobBuilder("dailySalesJob", jobRepository)
            .start(clearStatStep())      // 해당 기준일 기존 통계 삭제 (멱등성)
            .next(aggregateSalesStep())  // 집계 후 저장
            .build();
}

💡 GROUP BY 집계는 Reader의 SQL에서 DB에게 시키는 편이 효율적입니다. Reader가 이미 카테고리별로 합산된 행을 읽어 오면, Processor·Writer는 단순히 저장만 하면 됩니다.

집계 직전에 해당 기준일의 기존 통계를 지우는 clearStatStep을 두면, 같은 날짜를 다시 돌려도 결과가 정확히 한 벌만 남습니다(7장과 같은 멱등성 패턴).

⚠️ "오늘" 같은 상대 날짜를 배치 안에서 LocalDate.now()로 직접 구하지 마세요. 재실행·지연 실행 시 엉뚱한 날짜가 집계됩니다. 기준일은 항상 밖에서 파라미터로 주입해, 어제 새벽에 실패한 6월 29일 집계를 오늘 다시 돌려도 6월 29일이 집계되게 합니다.

8.4 대시보드에 연결하기

집계 테이블이 있으면 화면은 단순 조회입니다. 4장의 운영 콘솔에 통계 카드를 추가합니다.

@GetMapping("/stats")
public String stats(@RequestParam(required = false) String date, Model model) {
    LocalDate target = (date != null) ? LocalDate.parse(date) : LocalDate.now().minusDays(1);
    model.addAttribute("rows", statRepository.findByStatDate(target));
    return "admin/stats";
}
<table class="w-full text-sm">

수백만 건을 매번 집계하던 화면이, 집계 테이블 수십 행 조회로 바뀌어 즉시 응답합니다.

🧪 실습 — 일별 매출 집계

  1. orders에 며칠치 주문을 카테고리를 섞어 넣습니다.
  2. date를 바꿔 가며 dailySalesJob을 실행해 daily_sales_stat을 채웁니다.
  3. /admin/stats?date=...에서 날짜별 매출이 맞게 나오는지 확인합니다.
  4. 특정 날짜를 다시 집계해도(삭제 후 재생성) 행이 중복되지 않고 숫자가 동일한지 확인합니다.

이 장의 요점

  • 통계는 무거운 집계를 새벽에 미리 해 두고 화면은 가벼운 조회만 하게 만드는 패턴입니다.
  • 기준일을 JobParameter로 주입하면 특정 날짜만 다시 집계할 수 있고, clearStatStep + 복합 PK로 멱등성을 보장합니다.
  • GROUP BY 집계는 Reader의 SQL에서 DB에게 시키면 효율적이며, 화면은 집계 테이블만 조회해 즉시 응답합니다.
