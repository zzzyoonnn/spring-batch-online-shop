17장. 운영: 스케줄링·재시작·모니터링

이 장에서 배우는 것

  • @Scheduled로 배치를 정해진 시각에 자동 실행하기
  • 실패한 Job을 재시작하는 원리와 메타테이블 활용
  • 실행 이력 추적과 실패 알림으로 운영 가능한 시스템 완성하기

17.1 스케줄러와 배치를 함께 쓰기

1장에서 "스케줄러가 곧 배치는 아니다"라고 했습니다. 둘은 역할이 다르고, 함께 씁니다. @Scheduled가 언제를 정하고, JobLauncher가 무엇을 안전하게 실행합니다.

@Component
@RequiredArgsConstructor
public class SettlementScheduler {

    private final JobLauncher jobLauncher;
    private final Job dailySettlementJob;

    @Scheduled(cron = "0 0 3 * * *") // 매일 새벽 3시
    public void runDailySettlement() throws Exception {
        String yesterday = LocalDate.now().minusDays(1).toString();
        JobParameters params = new JobParametersBuilder()
                .addString("date", yesterday) // 기준일을 명시적으로 주입
                .toJobParameters();
        jobLauncher.run(dailySettlementJob, params);
    }
}

기준일을 LocalDate.now().minusDays(1)로 계산해 파라미터로 명시적으로 넘기는 것이 중요합니다. 배치 내부에서 "오늘"을 다시 구하면 재실행 시 날짜가 어긋납니다(8장). 스케줄러가 날짜를 한 번 정해 넘기면, 그 실행은 늘 같은 날짜를 처리합니다.

💡 4장에서 만든 화면 실행과 17장의 스케줄 실행은 같은 JobLauncher를 씁니다. 평상시엔 스케줄러가 자동 실행하고, 실패 시엔 관리자가 화면에서 같은 Job을 수동 재실행하는 식으로 둘을 보완적으로 운영합니다.

17.2 재시작의 원리

Spring Batch의 가장 강력한 기능이 재시작(restart)입니다. 실패한 Job을 같은 JobParameters로 다시 실행하면, 처음부터가 아니라 실패한 지점부터 이어 갑니다. 이것을 가능하게 하는 것이 2장에서 만든 메타테이블입니다.

BATCH_STEP_EXECUTION_CONTEXT 에 "어디까지 읽었는지"가 저장됨
 → 재시작 시 그 지점부터 Reader가 이어 읽음
 → 이미 COMPLETED된 Step은 건너뜀

예를 들어 3개 Step짜리 Job이 Step 2에서 실패했다면, 같은 파라미터로 재실행 시 Step 1은 건너뛰고 Step 2부터 시작합니다.

⚠️ 재시작이 "이어서" 동작하려면 같은 JobParameters여야 합니다. 4장에서 단순 작업에 넣었던 runAt=현재시각을 정산·통계 같은 재시작 대상 Job에 넣으면, 매번 새 실행으로 취급돼 이어받지 못합니다. 재시작이 필요한 Job은 의미 있는 파라미터(기준일 등)만 쓰세요.

💡 멱등하게 설계한 배치(7·8장)는 재시작이 더 쉽습니다. 처음부터 다시 돌려도 결과가 같으니, "이어서"가 아니라 "통째로 다시"도 안전한 선택지가 됩니다.

17.3 실행 이력 추적

운영에서는 "성공했는지"보다 "어디까지 성공했고 어디서 실패했는지"가 더 중요합니다. 메타테이블이 그 답을 담고 있습니다.

BATCH_JOB_INSTANCE    어떤 Job이 어떤 파라미터로 정의됐나
BATCH_JOB_EXECUTION   각 실행의 성공/실패/시작·종료 시각
BATCH_STEP_EXECUTION  Step별 읽기/쓰기/스킵/커밋 건수와 상태
-- 최근 실패한 실행과 원인 보기
SELECT e.job_execution_id, i.job_name, e.status, e.exit_message
FROM BATCH_JOB_EXECUTION e
JOIN BATCH_JOB_INSTANCE i ON e.job_instance_id = i.job_instance_id
WHERE e.status = 'FAILED'
ORDER BY e.job_execution_id DESC;

4장에서 만든 운영 콘솔의 이력 표가 바로 이 데이터를 JobExplorer로 읽어 보여 주는 것입니다. Step별 READ_COUNT·WRITE_COUNT·SKIP_COUNT까지 화면에 노출하면, "1만 건 중 9,980건 처리, 20건 스킵"을 한눈에 파악할 수 있습니다.

💡 버전 메모 — Spring Batch 6에서는 JobRepository가 JobExplorer를, JobOperator가 JobLauncher를 상속하므로, 조회·실행을 각각 JobRepository·JobOperator 하나로 통합할 수 있습니다(4장·부록 A 참고). 이 장의 코드는 메서드 이름이 같아 그대로 동작합니다.

17.4 실패 알림

새벽에 돌아간 배치가 실패했는데 아침까지 아무도 모르면 안 됩니다. Job 실행에 리스너를 붙여 실패 시 알림을 보냅니다.

@Component
public class JobAlertListener implements JobExecutionListener {
    @Override
    public void afterJob(JobExecution jobExecution) {
        if (jobExecution.getStatus() == BatchStatus.FAILED) {
            // 슬랙/메일 등으로 "OO 배치 실패" 알림 전송
            alertService.notifyFailure(jobExecution);
        }
    }
}

💡 알림에는 Job 이름, 파라미터(기준일), 실패한 Step, exitMessage를 담으면 좋습니다. 받자마자 화면에서 같은 Job을 재실행할지, 데이터를 고친 뒤 돌릴지 판단할 수 있습니다.

17.5 마켓온, 운영에 들어가다

여기까지 오면 마켓온은 완성된 운영 배치 시스템입니다. 처음 그렸던 그림을 다시 봅니다.

@Scheduled  → 정해진 시각에 자동 실행
JobLauncher → Job을 안전하게 실행 (화면/스케줄 공용)
메타테이블   → 어디까지 됐는지 기록 → 재시작 근거
JobExplorer → 운영 콘솔에 이력 표시
Listener    → 실패 시 즉시 알림

그리고 이 모든 사례를 관통하는 한 문장으로 돌아옵니다.

"한 번에 다 하지 말고 — 작게 나눠 처리하고, 다시 돌려도 안전하게."

CSV든 정산이든 삭제든, 우리가 만든 모든 배치는 청크로 작게 나눴고(Chunk), 다시 돌려도 결과가 망가지지 않게(멱등성·재시작) 설계했습니다. 사례는 달라도 좋은 배치의 원리는 늘 이 문장으로 수렴합니다.

🧪 실습 — 운영 시나리오 점검

  1. 정산 배치에 새벽 3시 @Scheduled를 걸고, 다음 날 자동 실행과 이력을 확인합니다.
  2. 일부러 중간에 실패하도록 데이터를 만들어 Job을 실패시킨 뒤, 같은 파라미터로 재시작해 실패 지점부터 이어지는지 확인합니다.
  3. JobAlertListener로 실패 알림이 오는지 확인합니다.
  4. 운영 콘솔에서 Step별 읽기/쓰기/스킵 건수가 보이도록 이력 화면을 보강합니다.

이 장의 요점

  • @Scheduled로 실행 시각을 정하고 JobLauncher로 안전하게 실행하며, 기준일은 스케줄러가 명시적으로 파라미터로 넘깁니다.
  • 재시작은 메타테이블에 저장된 진행 상태로 실패 지점부터 이어 가며, 이를 위해선 같은 JobParameters와 멱등 설계가 필요합니다.
  • 실행 이력은 메타테이블·JobExplorer로 추적하고, 실패는 리스너로 즉시 알려 운영 가능한 시스템을 완성합니다.

책을 마치며 여러분의 손에는 이제 동작하는 마켓온 운영 배치 시스템과, 새로운 사례를 만났을 때 "어떻게 나누고, 어떻게 다시 돌려도 안전하게 만들까"를 스스로 답하는 사고 틀이 남았습니다. 부록에서 자주 쓰는 참조와 설계 체크리스트를 정리했으니, 실무에서 곁에 두고 활용하세요.
