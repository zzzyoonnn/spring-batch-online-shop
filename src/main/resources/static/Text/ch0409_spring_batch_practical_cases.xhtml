9장. 휴면 회원 전환

이 장에서 배우는 것

  • 휴면 전환처럼 실시간이 필요 없는 작업을 새벽 배치로 처리하기
  • 상태 변경 Step과 알림 발송 대상 생성 Step을 분리하는 이유
  • 한 Job 안에서 여러 Step을 흐름으로 엮기

9.1 사례 이해: 급하지 않은 일

마켓온은 1년 이상 로그인하지 않은 회원을 휴면 상태로 전환합니다.

1년 이상 로그인하지 않은 회원 조회
 → 휴면 전환 대상 여부 확인
 → 회원 상태 변경
 → 휴면 안내 발송 대상 저장

탈퇴 예정 회원 정리, 장기 미사용 쿠폰 만료, 비활성 계정 잠금, 마케팅 수신 동의 만료 확인이 같은 패턴입니다. 이런 작업의 공통점은 사용자 요청에 즉시 반응할 필요가 없다는 것입니다. 매일 새벽 2시처럼 트래픽이 적은 시간에 돌리면 됩니다.

📌 핵심: 실시간성이 필요 없는 회원 상태 변경은 배치의 전형적인 영역입니다. 사용자가 기다리지 않으니 새벽에 여유롭게 처리합니다.

9.2 왜 Step을 분리하는가

휴면 전환은 두 가지 일을 합니다. ① 회원 상태를 ACTIVE에서 DORMANT로 바꾸고, ② 휴면 안내 메일/SMS 발송 대상을 만듭니다. 이 둘을 한 Step에 섞으면 문제가 생깁니다.

만약 상태 변경은 성공했는데 알림 발송 단계에서 메일 서버 장애로 실패한다면? 한 Step에 묶여 있으면 상태 변경까지 롤백되거나, 어디까지 처리됐는지 알기 어려워집니다. 단계를 나누면 각 단계를 독립적으로 재실행할 수 있습니다.

Step 1: 휴면 전환 대상 조회 및 상태 변경
Step 2: 알림 발송 대상 테이블 생성
Step 3: 이메일/SMS 발송 시스템에 전달
@Bean
public Job dormantMemberJob() {
    return new JobBuilder("dormantMemberJob", jobRepository)
            .start(convertDormantStep())     // Step 1: 상태 변경
            .next(createNotifyTargetStep())  // Step 2: 알림 대상 생성
            .build();
}

💡 Step 3(실제 발송)은 배치 안에서 직접 하기보다 외부 알림 시스템에 맡기는 편이 안정적입니다. 10장에서 자세히 다룹니다. 배치는 "누구에게 보낼지"만 정하고, "보내는 일"은 발송 전용 시스템이 합니다.

9.3 Step 1: 상태 변경

대상 조회는 마지막 로그인 일자가 1년 이전인 회원입니다. 기준일을 파라미터로 받아 재실행에 안전하게 만듭니다.

@Bean
@StepScope
public JdbcPagingItemReader<Member> dormantTargetReader(
        @Value("#{jobParameters['baseDate']}") String baseDate) {
    // WHERE status = 'ACTIVE' AND last_login_at < (baseDate - 1년)
    // ...
}

@Component
public class DormantProcessor implements ItemProcessor<Member, Member> {
    @Override
    public Member process(Member m) {
        m.markDormant(); // status = DORMANT, dormant_at = now
        return m;
    }
}

Writer는 JpaItemWriter나 JdbcBatchItemWriter로 변경된 회원을 저장합니다. 이미 DORMANT인 회원은 Reader의 WHERE status='ACTIVE' 조건 덕분에 다시 잡히지 않으므로, 재실행해도 안전합니다(멱등성).

⚠️ 휴면 전환은 법적·정책적 영향이 큰 작업입니다. 전환 기준(몇 개월/년), 사전 안내 의무, 휴면 해제 절차를 업무 규칙·관련 법령과 맞춰야 합니다. 코드보다 정책 합의가 먼저입니다.

9.4 Step 2: 알림 발송 대상 생성

상태가 바뀐 회원을 알림 발송 대상 테이블에 적재합니다. 실제 발송은 하지 않고 "보낼 명단"만 만듭니다.

CREATE TABLE notification_target (
    id          BIGINT AUTO_INCREMENT PRIMARY KEY,
    member_id   BIGINT      NOT NULL,
    type        VARCHAR(40) NOT NULL,  -- DORMANT_NOTICE 등
    channel     VARCHAR(20) NOT NULL,  -- EMAIL/SMS/PUSH
    status      VARCHAR(20) NOT NULL,  -- READY/SENT/FAILED
    created_at  DATETIME    NOT NULL,
    UNIQUE KEY uk_target (member_id, type)  -- 중복 발송 방지
);

UNIQUE (member_id, type)로 같은 회원에게 같은 종류의 안내가 중복 적재되는 것을 막습니다. 이 테이블은 10장에서 본격적으로 다룹니다.

🧪 실습 — 휴면 전환 2-Step Job

  1. member에 마지막 로그인이 1년 넘은 회원과 최근 로그인한 회원을 섞어 넣습니다.
  2. baseDate를 파라미터로 dormantMemberJob을 실행합니다.
  3. 대상 회원만 DORMANT로 바뀌고, notification_target에 DORMANT_NOTICE 행이 생겼는지 확인합니다.
  4. 다시 실행해 보고, 이미 휴면인 회원이 다시 잡히지 않고 알림 대상도 중복되지 않는지 확인합니다.

이 장의 요점

  • 휴면 전환처럼 실시간성이 없는 회원 상태 변경은 트래픽 적은 새벽에 배치로 처리합니다.
  • "상태 변경"과 "알림 발송 대상 생성"을 별도 Step으로 분리하면 각 단계를 독립적으로 재실행할 수 있습니다.
  • Reader의 상태 조건(WHERE status='ACTIVE')과 알림 테이블의 UNIQUE 제약으로 재실행·중복에 안전하게 만듭니다.

다음 장에서는 9장에서 만든 notification_target을 더 깊이 들여다봅니다. 수신 동의와 중복 발송을 어떻게 거르고, 왜 배치가 직접 발송하지 않는지를 다룹니다.
