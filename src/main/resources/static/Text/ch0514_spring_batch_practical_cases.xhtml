14장. 검색 인덱스 동기화

14.1 사례 이해: DB와 검색 엔진 맞추기

검색 기능이 있는 서비스는 DB 데이터를 Elasticsearch·OpenSearch 같은 검색 엔진에 동기화합니다.

게시글/상품 DB 조회
 → 검색 문서 형태로 변환
 → 검색 엔진에 색인(index)

상품 검색 인덱스 재생성, 게시글 재색인, 사용자 검색 인덱스 동기화, 추천 시스템용 데이터 생성이 모두 이 사례입니다.

📌 핵심: 검색 엔진은 DB의 사본입니다. 둘이 어긋나면 "DB엔 있는데 검색은 안 되는" 문제가 생깁니다. 배치가 이 둘을 주기적으로 맞춥니다.

14.2 전체 재색인 vs 증분 색인

두 가지를 분리하는 것이 이 사례의 핵심 설계입니다.

전체 재색인 (full):
  모든 상품을 처음부터 다시 색인
  - 매핑/분석기 변경, 장애 복구, 데이터 정합성 회복 시
  - 무겁지만 가장 확실하다

증분 색인 (incremental):
  최근 수정된 상품만 색인
  - 평상시 주기적 동기화
  - 가볍고 빠르다

평소에는 증분 색인으로 가볍게 따라가고, 검색 정책이 바뀌거나 인덱스가 깨졌을 때 전체 재색인으로 통째로 다시 만듭니다.

@Bean
@StepScope
public JdbcPagingItemReader<Product> indexTargetReader(
        @Value("#{jobParameters['mode']}") String mode,
        @Value("#{jobParameters['since']}") String since) {
    // mode=full      → 전체 (WHERE 1=1)
    // mode=incremental → WHERE updated_at >= :since
    // ...
}

💡 증분 색인의 since는 11장의 증분 처리와 같은 아이디어입니다. "마지막으로 색인한 시각" 이후 수정된 행만 골라 보냅니다.

14.3 Custom ItemWriter로 색인 보내기

검색 엔진 색인은 Custom ItemWriter로 구현합니다. Writer는 Chunk(묶음)를 받으므로, 검색 엔진의 벌크(bulk) API로 한 번에 여러 문서를 보내면 효율적입니다.

@Component
@RequiredArgsConstructor
public class ProductSearchWriter implements ItemWriter<SearchDocument> {

    private final SearchClient searchClient;

    @Override
    public void write(Chunk<? extends SearchDocument> chunk) {
        // chunk.getItems()를 한 번의 bulk 요청으로 색인
        searchClient.bulkIndex(chunk.getItems());
    }
}

💡 Spring Batch 5에서 ItemWriter.write()는 List가 아니라 Chunk<T>를 받습니다. chunk.getItems()로 묶음을 꺼내 검색 엔진 bulk API에 그대로 넘기면, 1건씩 보내는 것보다 훨씬 빠릅니다.

Processor는 DB 엔티티를 검색 문서로 변환합니다.

@Component
public class ProductDocProcessor implements ItemProcessor<Product, SearchDocument> {
    @Override
    public SearchDocument process(Product p) {
        return SearchDocument.builder()
                .id(p.getId())
                .name(p.getName())
                .categoryCode(p.getCategoryCode())
                .price(p.getPrice())
                .build();
    }
}

14.4 안정적으로 대량 색인하기

수백만 건을 한 번에 보내면 검색 엔진이 과부하에 빠집니다. Chunk 크기로 한 번에 보내는 양을 조절하고, 전체 재색인은 무중단으로 하려면 새 인덱스에 색인 후 별칭(alias)을 전환하는 방식을 씁니다.

1. product_v2 인덱스에 전체 색인 (서비스는 여전히 product_v1 조회)
2. 색인 완료 후 alias를 product_v1 → product_v2로 전환
3. product_v1 제거

이렇게 하면 재색인 중에도 검색이 멈추지 않고, 실패하면 기존 인덱스를 그대로 두면 됩니다.

⚠️ 색인 도중 실패에 대비해, 어디까지 보냈는지 추적할 수 있어야 합니다. 증분 색인은 처리 완료 시각을 기록해 다음 실행이 이어받게 하고, 전체 재색인은 별칭 전환 방식으로 "완성된 인덱스로만 전환"되게 합니다. 검색 엔진별 구체적 API는 공식 문서로 확인하세요.

🧪 실습 — 상품 증분 색인

  1. product 테이블과 검색 엔진(또는 목 클라이언트)을 준비합니다.
  2. mode=full로 전체 색인 Job을 돌려 초기 인덱스를 만듭니다.
  3. 상품 몇 건을 수정하고 mode=incremental&since=...로 증분 색인을 돌려, 수정된 건만 색인되는지 확인합니다.
  4. Chunk 크기를 바꿔 bulk 요청 크기가 달라지는 것을 관찰합니다.

이 장의 요점

  • 검색 인덱스 동기화는 DB의 사본인 검색 엔진을 주기적으로 맞추는 작업입니다.
  • 평상시 증분 색인(updated_at 기준), 정책 변경·장애 시 전체 재색인으로 분리해 운영합니다.
  • Custom Writer에서 Chunk를 검색 엔진 bulk API로 보내고, 전체 재색인은 새 인덱스 색인 후 별칭 전환으로 무중단 처리합니다.
