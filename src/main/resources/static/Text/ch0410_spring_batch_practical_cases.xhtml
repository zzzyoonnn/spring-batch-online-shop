10장. 알림 발송 대상 생성

이 장에서 배우는 것

  • 복잡한 조건으로 알림 대상자를 추출하고 중복 발송을 막는 법
  • 배치가 직접 발송하지 않고 발송 대상 테이블·메시지 큐에 넘기는 구조
  • 수신 동의·발송 상태를 함께 관리해 사고를 막기

10.1 사례 이해: 누구에게 보낼지 정하기

이메일·문자·푸시를 보낼 대상자를 추출하는 일은 그 자체로 하나의 배치 업무입니다. 쿠폰 만료 3일 전 사용자를 예로 들겠습니다.

쿠폰 만료 3일 전 사용자 조회
 → 수신 동의 여부 확인
 → 중복 발송 여부 확인
 → 알림 발송 대상 테이블 저장

쿠폰 만료 알림, 장바구니 미구매 알림, 결제 실패 알림, 구독 갱신 예정 알림, 휴면 전환 예정 알림, 이벤트 대상자 추출이 모두 같은 구조입니다.

📌 핵심: 대상자가 많고 조건이 복잡할수록, 그리고 "같은 사람에게 같은 알림이 중복 발송되면 안 될"수록 배치가 적합합니다.

10.2 배치는 발송하지 않는다

가장 중요한 설계 원칙입니다. 배치가 푸시·메일을 직접 보내면 여러 문제가 생깁니다. 외부 발송 API가 느리거나 실패하면 배치 전체가 지연·실패하고, 어디까지 보냈는지 추적이 어렵고, 재시도 시 중복 발송이 발생합니다.

그래서 배치는 "보낼 명단"만 만들고, 실제 발송은 전용 시스템에 맡깁니다.

Spring Batch
 → notification_target 테이블에 대상 적재 (status=READY)
 → 알림 서버/메시지 큐가 가져가 발송 (status=SENT/FAILED)

💡 이렇게 책임을 나누면 배치는 "조건에 맞는 대상 추출"에만 집중하고, 발송 시스템은 "대량 발송·재시도·결과 추적"에만 집중합니다. 각자 잘하는 일만 하므로 둘 다 단순해집니다.

10.3 대상 추출: 동의와 중복 거르기

대상 추출 Processor는 두 가지를 거릅니다. ① 마케팅 수신에 동의한 사용자인가, ② 이미 같은 알림을 받았는가.

@Component
@RequiredArgsConstructor
public class CouponExpiryNotifyProcessor
        implements ItemProcessor<CouponHolder, NotificationTarget> {

    private final NotificationTargetRepository targetRepository;

    @Override
    public NotificationTarget process(CouponHolder holder) {
        if (!holder.isMarketingAgreed()) {
            return null; // 수신 미동의 → 필터링 (Writer로 안 넘어감)
        }
        boolean already = targetRepository.existsByMemberIdAndType(
                holder.getMemberId(), "COUPON_EXPIRY");
        if (already) {
            return null; // 이미 대상에 있음 → 필터링
        }
        return NotificationTarget.ready(holder.getMemberId(), "COUPON_EXPIRY", "PUSH");
    }
}

Processor가 null을 반환하면 그 건은 Writer로 넘어가지 않습니다(3장에서 본 필터링). 동의하지 않은 사용자나 이미 발송 대상인 사용자가 자연스럽게 걸러집니다.

⚠️ 수신 동의 확인은 선택이 아니라 의무입니다. 광고성 정보 전송은 사전 동의(옵트인)와 수신 거부 처리가 법으로 규정돼 있습니다. 동의 여부와 동의 시각을 데이터로 관리하고, 배치에서 반드시 확인하세요.

10.4 중복 방지의 이중 안전장치

코드에서 existsBy...로 거르더라도, 동시 실행이나 타이밍 문제로 같은 대상이 두 번 들어갈 수 있습니다. 9장에서 만든 UNIQUE 제약이 마지막 방어선입니다.

UNIQUE KEY uk_target (member_id, type)

이 제약이 있으면, 코드 체크를 통과한 중복도 DB가 거부합니다. 배치는 이 위반을 Skip 처리해 나머지 대상은 정상 적재합니다(5장의 Skip 패턴).

💡 "코드 체크 + DB 제약"의 이중 구조는 이 책 전반의 멱등성 패턴입니다(7장 정산, 8장 통계, 9장 알림). 외워 두면 거의 모든 사례에 그대로 적용됩니다.

10.5 발송 상태 관리

발송 시스템이 처리한 결과는 status로 돌아옵니다.

READY  → 발송 대기 (배치가 적재한 상태)
SENT   → 발송 완료 (발송 시스템이 갱신)
FAILED → 발송 실패 (재시도 대상)

배치는 보통 READY만 만들고, 발송 결과 갱신은 발송 시스템이 합니다. 화면에서는 status별 건수를 보여 줘 "오늘 쿠폰 만료 알림 1,204건 중 1,180건 발송, 24건 실패"를 한눈에 파악하게 합니다.

🧪 실습 — 쿠폰 만료 알림 대상 추출

  1. 만료가 임박한 쿠폰을 보유한 회원과, 수신 미동의 회원을 섞어 데이터를 만듭니다.
  2. 만료 3일 전 대상을 추출하는 Job을 만들어 실행합니다.
  3. 동의한 회원만 notification_target에 READY로 적재됐는지, 미동의 회원은 빠졌는지 확인합니다.
  4. 다시 실행해 같은 회원이 중복 적재되지 않는지(코드 체크 + UNIQUE) 확인합니다.

이 장의 요점

  • 복잡한 조건의 알림 대상자 추출은 배치의 전형적 업무이며, 수신 동의와 중복 발송 여부를 Processor에서 거릅니다.
  • 배치는 발송하지 않고 notification_target에 명단만 적재하며, 실제 발송은 전용 시스템·메시지 큐가 맡습니다.
  • 코드 체크 + DB UNIQUE 제약의 이중 안전장치로 중복 발송을 막고, status로 발송 생애주기를 추적합니다.

다음 장에서는 방향을 바꿔, 쌓인 로그·이벤트 데이터를 분석용으로 후처리하는 사례를 다룹니다. 원본은 절대 건드리지 않고 요약·집계 테이블만 만드는 원칙이 핵심입니다.
