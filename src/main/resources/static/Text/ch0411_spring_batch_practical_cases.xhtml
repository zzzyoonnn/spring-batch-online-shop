11장. 로그·이벤트 데이터 후처리

이 장에서 배우는 것

  • 대량 로그를 매시간/매일 모아 분석용 테이블로 변환하기
  • 원본 로그를 보존하고 가공 결과만 별도 테이블에 쌓는 원칙
  • 처리 기준 시각으로 증분 처리하기

11.1 사례 이해: 많고, 급하지 않은 데이터

서비스 로그나 이벤트 데이터를 분석용 테이블로 변환하는 작업입니다.

이벤트 로그 조회
 → 유효 이벤트 필터링
 → 사용자 행동 단위로 집계
 → 분석 테이블 저장

클릭 로그 집계, 접속 로그 요약, 사용자 행동 이벤트 분석, 실패한 결제 이벤트 추적, 비정상 로그인 탐지 데이터 생성이 모두 여기에 속합니다. 로그 데이터는 양이 많지만 실시간 처리가 꼭 필요하지는 않은 경우가 많아, 매시간 또는 매일 모아서 처리하면 시스템 부하를 줄일 수 있습니다.

📌 핵심: 로그 후처리는 "많지만 급하지 않은" 데이터의 전형입니다. 모아서 한 번에 처리해 실시간 시스템의 부하를 덜어 줍니다.

11.2 원본은 건드리지 않는다

로그 후처리의 황금률입니다. 원본 로그는 수정·삭제하지 않고, 처리 결과를 별도 테이블에 저장합니다.

raw_event_log      (원본, 읽기만)
 → event_summary    (사용자·행동 단위 요약)
 → dashboard_metric (대시보드용 지표)

원본을 보존하면 집계 로직이 바뀌었을 때 처음부터 다시 집계할 수 있고, 분석 결과가 의심스러울 때 원본과 대조할 수 있습니다. 원본을 가공하며 덮어쓰면 이런 안전망이 사라집니다.

⚠️ "공간을 아끼려고" 원본 로그를 가공 후 삭제하는 유혹을 조심하세요. 한 번 지운 원본은 복구할 수 없습니다. 오래된 원본을 정리하는 것은 별개의 아카이빙 작업으로 분리합니다(12장).

11.3 증분 처리: 처리 시각 기준으로 이어서

로그는 계속 쌓이므로, 매번 전체를 다시 집계하면 낭비입니다. 마지막으로 처리한 시각 이후의 로그만 읽는 증분 처리를 씁니다.

@Bean
@StepScope
public JdbcPagingItemReader<EventLog> eventLogReader(
        @Value("#{jobParameters['from']}") String from,
        @Value("#{jobParameters['to']}") String to) {
    // WHERE event_time >= :from AND event_time < :to
    // ORDER BY event_time, id
    // ...
}

from(이전 처리 완료 시각)과 to(이번 실행 기준 시각)를 파라미터로 받아, 그 사이 구간만 처리합니다. 매시간 실행이라면 직전 한 시간만 집계됩니다.

💡 처리 구간을 [from, to)처럼 시작은 포함, 끝은 제외로 잡는 것이 안전합니다. 그래야 다음 실행이 to부터 이어받아 경계의 로그가 빠지거나 두 번 처리되지 않습니다.

11.4 집계와 저장

Processor에서 유효 이벤트만 거르고, Writer에서 요약 테이블에 적재합니다. 사용자별·행동별 집계가 필요하면 Reader의 SQL에서 GROUP BY로 미리 묶어 오는 편이 효율적입니다(8장과 동일).

@Component
public class EventProcessor implements ItemProcessor<EventLog, EventSummary> {
    @Override
    public EventSummary process(EventLog log) {
        if (!log.isValid()) {
            return null; // 봇 트래픽·테스트 이벤트 등 무효 이벤트 필터링
        }
        return EventSummary.from(log);
    }
}

집계 결과 테이블에도 멱등성을 위해 복합 키를 둡니다. 예컨대 시간대별 클릭 요약이라면 (summary_hour, page_id)를 PK로 두고, 재집계 시 해당 구간을 지운 뒤 다시 채웁니다.

🧪 실습 — 시간대별 클릭 요약

  1. raw_event_log에 클릭 이벤트를 시각을 다양하게 섞어 넣습니다(일부 무효 이벤트 포함).
  2. from/to로 한 시간 구간을 지정해 집계 Job을 실행합니다.
  3. event_summary에 유효 이벤트만 집계됐는지, 원본 raw_event_log는 그대로인지 확인합니다.
  4. 같은 구간을 다시 집계해도 결과가 중복되지 않는지 확인합니다.

이 장의 요점

  • 로그·이벤트 후처리는 "많지만 급하지 않은" 데이터를 매시간/매일 모아 분석용으로 변환하는 작업입니다.
  • 원본 로그는 읽기만 하고, 가공 결과는 event_summary·dashboard_metric 같은 별도 테이블에 저장합니다.
  • [from, to) 시각 구간으로 증분 처리하고, 집계 테이블에 복합 키를 두어 재집계에 안전하게 만듭니다.

다음 장에서는 쌓이기만 하는 데이터를 정리하는 사례를 다룹니다. 오래된 로그를 아카이브로 옮기고 삭제할 때, DB에 부담을 주지 않도록 Chunk 단위로 나눠 처리하는 법을 배웁니다.
